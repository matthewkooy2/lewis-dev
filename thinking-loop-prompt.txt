## Goal

Create a host-controlled Freestyle loop resembling:

```text
inspect and gather context
→ plan
→ critique plan
→ revise if needed
→ generate edit bundle
→ validate bundle
→ apply inside isolated worktree
→ run allowlisted checks
→ diagnose failures
→ generate targeted repair bundle
→ revalidate and reapply
→ repeat within limits
→ review final diff against the original goal
→ stop for human approval
```

This is not an unlimited “keep asking the model” loop. Each model call should have a narrow role and receive fresh, relevant evidence.

## Loop stages

Use clearly separated stages such as:

* Planner
* Plan critic
* Implementer
* Diagnostician
* Repairer
* Final reviewer

Store concise structured artifacts from each stage. Do not depend on endlessly appending all previous prompts and responses.

Persist enough loop state to resume or inspect a job after Lewis or the PC restarts, including:

* Original goal
* Current plan
* Relevant files and evidence
* Attempts made
* Generated bundles
* Validation failures
* Applied diffs
* Commands and test results
* Diagnoses
* Repairs
* Stop reason
* Final review

Do not store or request hidden chain-of-thought. Store concise decisions, evidence, assumptions, diagnoses, and next actions.

## Context gathering

Use the existing repository map, user-named files, imports, failed-test locations, and the new code-tracing subsystem to select compact context.

Trace information may include:

* Target symbols
* Important callers and callees
* Injected callbacks
* Side effects
* Relevant tests
* Files connected to the requested change

Treat tracing as one ranking signal, not the sole source of truth. Keep context bounded for Qwen and report when required context was omitted.

## Structured output

Correct the LM Studio structured-output support.

The provider capability must distinguish at least:

* Plain text
* `json_object`
* `json_schema`

For this LM Studio setup, use a real `json_schema` payload when strict structured output is enabled. Supply the actual schema required for the stage rather than merely changing the type string.

Keep explicit text mode available. Do not silently switch modes or providers after a failure. Record the selected mode in artifacts.

Preserve raw malformed model responses in bounded diagnostic artifacts so failures can be investigated.

## Validation and repair behavior

Continue using Lewis’s deterministic validators as the authority.

Different failures should trigger different responses:

* Invalid JSON or schema shape: request a format-only repair.
* Unsafe path or prohibited operation: stop immediately; never retry around safety.
* Stale or missing edit anchor: provide the exact validation error and relevant current source.
* Applied patch with failing tests: run a diagnosis stage, then request the smallest targeted repair.
* Missing context: gather allowed context or stop honestly.
* Repeated identical failure: stop instead of looping.

The diagnostician should receive:

* Original goal
* Current plan
* Current diff
* Exact failed command
* Exit code
* Relevant failure output
* Relevant source and test snippets

The repairer should produce only a new validated edit bundle.

## Bounds and stop conditions

Use configurable conservative defaults, approximately:

* Up to 2 planning/critique passes
* 1 initial implementation attempt
* Up to 3 test-driven repair cycles
* 1 final review
* Maximum 10–12 total model calls
* One active local Freestyle job at a time
* A maximum wall-clock duration
* Bounded prompt and artifact sizes

Stop when:

* Required checks pass and final review has no blocking issue
* The same failure or materially identical patch repeats
* Progress stalls
* A safety validator rejects the operation
* Required context is unavailable
* The task requires prohibited network, secret, package-install, Git-remote, or external-workspace access
* The configured model-call or time limit is reached

Every stop should produce a clear reason and useful next action.

## Safety and approval boundary

Preserve all existing protections:

* Isolated worktree only
* No changes to the main checkout
* No arbitrary shell execution
* Only existing allowlisted checks
* No package installs
* No Git remotes
* No commits, merges, or pushes
* No secret or runtime-file access
* No changes outside declared and validated paths

The loop may automatically apply validated bundles only inside its isolated worktree so it can run tests and repairs.

It must always stop before integration into the user’s branch. Final output should show the diff, tests, attempts, unresolved concerns, and review findings for human approval.
